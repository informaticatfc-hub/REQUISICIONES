## 3. Descripción detallada por tipo de usuario

---

### 3.1 Administrador (`admin`) — Nivel 100

El administrador es el único usuario con **acceso total e irrestricto** al sistema. Sus responsabilidades principales son:

#### Gestión de usuarios
- Crea, edita y desactiva cuentas de usuario.
- Asigna uno o varios roles a cada usuario (sistema N:M).
- Asigna las obras a cada residente o usuario de campo.
- Debe poder restablecer contraseñas directamente desde el panel (**actualmente requiere acceso a BD**).

#### Gestión de roles y permisos
- Accede al panel de administración (`admin.php`) con las secciones: **Usuarios**, **Roles** y **Auditoría**.
- Crea nuevos roles y define qué permisos atómicos (`modulo.accion`) tiene cada uno.
- **Limitación conocida:** los roles desactivados no pueden reactivarse desde la UI — solo desde SQL.

#### Auditoría
- Visualiza el log de auditoría generado por `tf_audit_log()`, que incluye acciones de presiones y usuarios.
- **Limitación conocida:** no hay filtros de búsqueda ni exportación CSV. Con muchos registros la tabla se vuelve inoperante.

#### Acceso a todos los módulos
- Puede crear, editar y eliminar: obras, requisiciones, hojas, ítems, presiones, proveedores, bancos, catálogos.
- Es el único que puede navegar a `admin.php`.
- Ve todos los KPIs y dashboards independientemente de la obra activa.

#### Flujo típico del administrador
```
Login → Panel Admin → Crear usuario → Asignar rol → Asignar obras
Login → Panel Admin → Auditoría → Revisar acciones de usuarios
Login → Cualquier módulo → Supervisar/corregir datos
```

---

### 3.2 Director (`director`) — Nivel 80

El director tiene **visibilidad global** del sistema sin capacidad de crear o modificar datos operativos. Su rol es estratégico: autoriza o rechaza presiones de pago y supervisa el estado financiero de las obras.

#### Dashboard KPI (`reportes_kpi.php` / `direccion.php`)
- Ve métricas globales de todas las obras: montos pagados, adeudados, presiones activas, número de requisiciones.
- **Limitación conocida:** no hay filtro por período (mes/trimestre/año); los datos son totales históricos.

#### Vista global de presiones (`all_presiones.php`)
- Accede a un grid tipo Excel con todas las presiones de todas las obras.
- Puede filtrar por obra, exportar a XLSX.
- Puede importar actualizaciones masivas de `pago_autorizado` via XLSX.
- **Limitación conocida:** carga todos los registros a la vez (sin paginación). No existe tab de "pendientes de autorización" filtrado por urgencia.

#### Autorización de presiones
- Cambia el estatus de una presión de `PENDIENTE` a `AUTORIZADA` o la rechaza.
- Desde mayo 2026 puede agregar un `comentario_director` al autorizar/rechazar (**la migración SQL existe pero la UI del campo aún no está terminada**).

#### Lo que el director NO puede hacer
- Crear o editar requisiciones, hojas, ítems.
- Gestionar usuarios, roles o permisos.
- Crear obras.
- Acceder al panel de administración.

#### Flujo típico del director
```
Login → all_presiones.php → Filtrar por obra → Revisar monto → Autorizar presión
Login → reportes_kpi.php → Ver resumen financiero mensual (hoy: solo histórico)
```

---

### 3.3 Compras (`compras`) — Nivel 60

El rol de Compras es el más activo operativamente. Es quien gestiona el ciclo completo de una requisición desde su creación hasta que queda ligada a una presión de pago.

#### Requisiciones
- Crea nuevas requisiciones en las obras que tiene asignadas.
- Agrega hojas de requisición y los ítems de cada hoja (descripción, cantidad, precio unitario, proveedor).
- Edita requisiciones en estado `BORRADOR` o `PENDIENTE`.
- Valida/cambia estado de requisiciones.

#### Proveedores
- Crea y edita proveedores en el catálogo (`proveedores.php`, `agregar_proveedor.php`).
- Puede desactivar proveedores.

#### Enlazar requisiciones a presiones (`enlazar_requisiciones.php`)
- Selecciona requisiciones aprobadas y las liga a una presión de pago existente.
- **Limitación conocida:** no hay alerta cuando el monto acumulado de requisiciones supera el total de la presión.

#### Lo que Compras NO puede hacer
- Autorizar o marcar como pagada una presión.
- Gestionar usuarios o roles.
- Acceder al panel de administración.
- Ver el dashboard KPI global de dirección.

#### Flujo típico de Compras
```
Login → Seleccionar obra activa → requisiciones.php → Nueva Requisición
→ hojas_requisicion.php → Agregar hojas → items_requisicion.php → Agregar ítems
→ enlazar_requisiciones.php → Ligar a presión
```

---

### 3.4 Finanzas (`finanzas`) — Nivel 60

Finanzas controla el flujo de **pago efectivo** de las presiones ya autorizadas por el director. Gestiona también el catálogo de bancos.

#### Presiones de pago (`presiones.php`)
- Ve todas las presiones de las obras asignadas.
- Usa el tab **"Pendientes de pago"** (AUTORIZADA, no CERRADA) para identificar qué pagar.
- Marca presiones como pagadas (cambia estatus a `CERRADA`/`PAGADA`).
- **Limitación conocida:** no se solicita número de folio, banco o fecha de pago al cerrar la presión. Sin trazabilidad bancaria real.

#### Bancos (`bancos.php`)
- CRUD completo de bancos (nombre, número de cuenta, CLABE, etc.).
- **Limitación conocida:** los bancos no están vinculados a obras específicas; todos los bancos aparecen para todos.

#### Lo que Finanzas NO puede hacer
- Crear requisiciones ni presiones.
- Autorizar presiones (esa acción es del director).
- Gestionar usuarios, roles o el panel admin.
- Acceder al dashboard KPI global.

#### Flujo típico de Finanzas
```
Login → presiones.php → Tab "Pendientes de pago" → Revisar monto → Marcar pagada
Login → bancos.php → Actualizar datos bancarios
```

---

### 3.5 Residente (`residente`) — Nivel 40

El residente es el usuario de campo. Crea las necesidades de compra en forma de requisiciones, limitado estrictamente a las **obras que le fueron asignadas por el administrador**.

#### Requisiciones (`requisiciones.php`)
- Ve solo las requisiciones de sus obras asignadas.
- Crea nuevas requisiciones y sus hojas e ítems.
- Ve el monto total de cada requisición en la lista (columna implementada).
- Ve el estatus (badges con color) de cada requisición.
- **Limitación conocida:** no hay timeline visual del progreso de aprobación; no sabe en qué etapa quedó su requisición sin navegar al detalle.

#### Consulta de catálogos y presiones (solo lectura)
- Puede ver el catálogo de proveedores y las presiones de sus obras, pero sin capacidad de crear ni editar.

#### Lo que el Residente NO puede hacer
- Ver obras distintas a las asignadas.
- Crear o editar presiones, proveedores, bancos.
- Autorizar o pagar presiones.
- Acceder al panel admin o al dashboard KPI global.

#### Flujo típico del Residente
```
Login → Seleccionar obra asignada → Nueva Requisición → Agregar hojas → Agregar ítems → Guardar
Login → Ver mis requisiciones → Revisar estatus
```

---

### 3.6 Lector / Auditor (`lector`) — Nivel 20

El lector tiene acceso de **solo lectura** a los módulos de sus obras asignadas. Se usa para auditores externos, supervisores o directivos que necesitan consultar sin modificar nada.

#### Qué puede ver
- Requisiciones de sus obras asignadas.
- Presiones de sus obras asignadas.
- Catálogo de proveedores y bancos.
- Log de auditoría (vista permitida por RBAC).

#### Qué NO puede hacer
- Ninguna operación de creación, edición o eliminación en ningún módulo.
- Acceder al panel admin.
- Ver KPIs globales del director.

#### Limitación principal
Los botones de CRUD (Agregar, Editar, Eliminar) aparecen en la UI aunque RBAC los bloquee en backend. El lector ve acciones que no puede ejecutar, lo que genera confusión. La solución es que el frontend oculte esos controles cuando el permiso no existe (en proceso, no generalizado aún).

## 4. Mejoras recomendadas

### 4.1 Prioridad inmediata (antes de producción)

#### [P1] Agregar cabeceras HTTP de seguridad
**Archivo:** `includes/layout_top.php` o `validarSesion.php`  
**Por qué:** sin `X-Frame-Options` el sistema es vulnerable a clickjacking. Sin `Content-Security-Policy` el XSS tiene mayor superficie.  
**Esfuerzo:** 30 minutos. Bajo riesgo de romper algo.

#### [P2] Mostrar / capturar comentario del director en la UI
**Archivos:** `pages/presiones_detalles.php`, `assets/js/presiones_detalles.js`, `api/crud_presionDetail.php`  
**Por qué:** la migración SQL `010` ya agrega el campo, pero la UI no lo muestra ni lo permite editar al director.  
**Esfuerzo:** 2-4 horas.

#### [P3] Reactivar roles inactivos desde el panel admin
**Archivos:** `pages/admin.php`, `api/crud_admin.php`  
**Por qué:** sin este botón, un rol desactivado por error solo se puede recuperar con acceso directo a la BD.  
**Esfuerzo:** 2-3 horas.

#### [P4] Eliminar `main.css` de `all_presiones.php`
**Archivo:** `pages/all_presiones.php` línea 44  
**Por qué:** `main.css` contiene reglas legacy v3 que pueden conflictuar con `v4.css` y romper el dark mode.  
**Esfuerzo:** 5 minutos. Verificar visualmente después.

---

### 4.2 Corto plazo (mejoras de alto impacto)

#### [CP1] Modal de pago con folio bancario (Finanzas)
Al marcar una presión como pagada, abrir un modal con campos:
- `folio_pago` — referencia bancaria obligatoria
- `banco_id` — selector del banco usado
- `fecha_pago` — fecha efectiva de pago  

Registrar en la tabla `presiones` (requiere migración SQL) y en `audit_log`.

#### [CP2] Filtros en log de auditoría del Admin
Agregar filtros de búsqueda server-side:
- Rango de fechas (`desde` / `hasta`)
- Usuario (`user_id`)
- Acción (`log_action LIKE ?`)
- Módulo afectado  

Agregar paginación server-side (LIMIT/OFFSET). Botón "Exportar CSV".

#### [CP3] Filtro de período en KPI (`reportes_kpi.php`)
Selector: Esta semana / Este mes / Este trimestre / Este año / Personalizado.  
Pasar `fecha_inicio` y `fecha_fin` a los endpoints de KPI y filtrar en la consulta SQL con `WHERE fecha BETWEEN ? AND ?`.

#### [CP4] Tab "Pendientes de autorización" en `all_presiones`
Agregar pestaña que filtre `presiones_estatus = 'PENDIENTE'`, ordenado por `presiones_fecha ASC` (más antiguo primero), para que el director priorice rápido.

#### [CP5] Alert de tope en `enlazar_requisiciones`
Al agregar una requisición a una presión, calcular en tiempo real:  
`monto presión - suma de requisiciones ya enlazadas - monto nueva requisición`  
Mostrar badge `⚠️ Excede presupuesto en $X` si el resultado es negativo.

#### [CP6] Columna subtotal por hoja en `hojas_requisicion`
Calcular `SUM(item_cantidad * item_precio)` por hoja y mostrarlo como columna en la tabla de hojas. Reduce el tener que entrar a cada hoja para saber el monto.

### 4.3 Mediano plazo

#### [MP1] Command Palette (`Ctrl+K`) funcional
La estructura HTML ya existe en `v4-layout.js`. Falta implementar:
- Indexado de obras, requisiciones y presiones recientes en un array JSON al cargar la página.
- Filtrado en tiempo real al escribir.
- Navegación por teclado (`↑`, `↓`, `Enter`).
- Acciones directas: "Nueva requisición", "Ir a obra X".

#### [MP2] Paginación server-side en `all_presiones`
Agregar `?page=N&per_page=50&obra_id=X` en el endpoint `crud_all_presiones.php`.  
Devolver `{ total, page, data: [...] }`.  
En el frontend, reemplazar la carga masiva por carga por página.

#### [MP3] Restablecimiento de contraseña desde el panel admin
Formulario en el perfil de usuario (admin ve todos los usuarios).  
Generar contraseña temporal o hash nuevo.  
Registrar cambio en `audit_log` con `log_action = 'user.password_reset'`.

#### [MP4] Pruebas E2E básicas con Playwright
Cubrir los flujos críticos:
- Login correcto / incorrecto / bloqueo por rate limiting.
- Crear requisición → agregar hoja → agregar ítem.
- Director autoriza presión.
- Finanzas marca como pagada.
